# `CREATE TABLE IF NOT EXISTS` is not safe against real concurrency

**What broke:** the app's schema migration (`ensureSchema()`) runs on every cold serverless instance, guarded only by an in-process cached promise - which does nothing for two *separate* instances racing on a database that doesn't have the tables yet (a first deploy, or several Vercel lambdas spinning up at once against a fresh Neon database). Reproduced directly: 12 concurrent sessions running the same `CREATE TABLE IF NOT EXISTS` sequence against an empty database failed 11 times out of 12 with `duplicate key value violates unique constraint "pg_type_typname_nsp_index"`. Postgres's own IF NOT EXISTS check-then-create isn't atomic across sessions - two sessions can both see "doesn't exist yet" and both try to create it.

**Why the obvious fixes don't work here:** a plain (non-transactional) advisory lock (`pg_advisory_lock`/`pg_advisory_unlock`) needs a persistent session to mean anything - but this app's DB access goes through Neon's HTTP driver, where by default every `await db\`...\`` call may use a different underlying connection. A lock taken in one call and "released" in a later, separate call isn't reliably guarding anything.

**The fix:** `pg_advisory_xact_lock()` instead - a *transaction-scoped* advisory lock that auto-releases at COMMIT or ROLLBACK, no separate unlock call needed. The entire migration (every `CREATE TABLE`, index, and one-time `ALTER`/backfill statement) now runs as one `sql.transaction([...])` call, with the lock acquisition as the first statement. Since the whole transaction is one HTTP request/session on Neon's driver, the lock's lifetime lines up correctly with the work it's guarding. Concurrent cold starts now queue up one at a time instead of racing; re-ran the same 12-concurrent-cold-start reproduction against a fresh database afterward and got 12/12 successes. See `ensureSchema()` in `src/lib/db.ts`.

**The reusable lesson:** "idempotent" (`IF NOT EXISTS`) and "safe under concurrency" are different properties - idempotent-but-racy code is fine for sequential retries and wrong for anything that might genuinely run at the same time. When a migration or setup routine might run concurrently (multiple serverless cold starts, multiple app instances on deploy), reach for a *transaction-scoped* advisory lock specifically when the underlying driver doesn't guarantee a stable session across separate calls - a plain session-level lock silently doesn't do what it looks like it does in that environment.

# Calendar-day logic needs the app's timezone, never raw UTC

**What broke:** streak continuation (`recordSessionComplete`), the weekly activity heatmap (`getWeeklyStats`), and the progress page's 7-day strip (`last7Days`) all derived "today"/"yesterday" by slicing `new Date().toISOString()` - which is always the UTC calendar date. Singapore is UTC+8, so the "day" rolls over at 8am local time, not midnight. Concretely: practising Monday 09:00 SGT then again Tuesday 07:00 SGT are both `2026-09-07` in UTC (verified: `2026-09-07T01:00:00Z` and `2026-09-07T23:00:00Z` both slice to the same UTC date) - the streak wouldn't increment even though the user genuinely practised on two different calendar days. The reverse case (practising early, then late) could wrongly burn the streak-freeze on a day that wasn't actually missed.

**Why it's an easy mistake:** `Date.prototype.toISOString()` is *always* UTC - there's no "local" variant on the primitive, and testing this locally (wherever the developer's machine's timezone happens to be) rarely lands on the exact boundary hours where it matters, so the bug hides until a real user in the target timezone hits it.

**The fix:** one shared module, `src/lib/date.ts`, exporting `APP_TIMEZONE = "Asia/Singapore"` and `dateKeyInAppTimezone(date)` built on `Intl.DateTimeFormat("en-CA", { timeZone: APP_TIMEZONE, ... })` (the `"en-CA"` locale formats as `YYYY-MM-DD` directly, no manual reassembly). Every place that needs "what calendar day is this" - `todayKey()`, `daysAgoKey(n)`, and the SQL-side bucketing in `getWeeklyStats` (`created_at AT TIME ZONE 'Asia/Singapore'`) and `getAdminStats` (bound date-string parameters instead of Postgres's own `CURRENT_DATE`) - goes through this one place now, so there's a single spot to fix if the app ever needs multiple timezones instead of one fixed constant.

**The reusable lesson:** any time a feature cares about "today," "this week," or a day-to-day streak, ask explicitly "whose today?" before writing the date logic. If the app has one target audience in one timezone, hardcode that timezone in one shared, named place (`APP_TIMEZONE`) rather than letting `new Date()`'s implicit UTC leak into date-key logic scattered across files - and push the same timezone into any SQL that buckets by calendar day too, not just the JS side, or the two will disagree.

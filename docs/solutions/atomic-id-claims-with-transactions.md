# Claiming a shared resource needs a real transaction, not a check-then-act

**What broke:** renaming a visitor's anonymous id (`changeUserId`) checked `isUserIdAvailable(newId)` in one round trip, then issued five separate `UPDATE`s across five tables in a second round trip, with no transaction tying them together. Two problems, reproduced live against a local Postgres copy of the schema: (1) the availability check only looked at two of the five per-user tables, so an id with orphaned data in a third table (e.g. `question_progress` rows left over from an unrelated typo'd "resume" attempt) was wrongly reported as free — the rename then partially succeeded, leaving the user's data split across two ids with no rollback; (2) even with a correct check, two concurrent renames to the same brand-new id could both pass the check before either one wrote anything — a textbook time-of-check-to-time-of-use race.

**Why:** "check if it's free, then take it" is only safe if nothing can happen between the two steps. Over a stateless HTTP-per-query driver (Neon's serverless driver, in this case) there's no implicit locking between separate `await db\`...\`` calls — each one is its own round trip, and anything can interleave between them.

**The fix:** introduced a `users(user_id primary key)` registry table as the single source of truth for "does this id exist," and made the claim itself an `INSERT INTO users (user_id) VALUES ($1)` as the *first* statement inside a real transaction (`sql.transaction([...])`), followed by the five `UPDATE`s in the same transaction. The `INSERT`'s primary-key constraint is what actually prevents two concurrent claims of the same id — if it fails, the whole transaction rolls back atomically, so there's no partial state to clean up. The pre-check (`isUserIdAvailable`) still exists, but only as a cheap way to return a friendlier error in the common case — it is explicitly documented as not the actual safety guarantee. See `isUserIdAvailable`/`changeUserId` in `src/lib/db.ts`.

**The reusable lesson:** whenever "is X available, if so take it" shows up against shared state, ask whether the check and the take can be forced into one atomic operation (a unique constraint inside a transaction, `INSERT ... ON CONFLICT`, a compare-and-swap) — and if the answer is "they're two separate round trips right now," that's the bug, not a detail to fix later. A pre-check is fine as a UX nicety; it is never the safety mechanism on its own.

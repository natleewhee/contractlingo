# A renamed enum needs its defaults hunted down, not just its type

**What broke:** the Site Diary redesign renamed every avatar scheme id (e.g. `"coral"` became `"marker-coral"`). The type (`AvatarSchemeId`) and the picker UI were updated, but three other places still had the old literal `"coral"` hardcoded: the Postgres column default (`avatar_scheme text NOT NULL DEFAULT 'coral'`), and two in-code fallback constants (`DEFAULT_PROFILE`/`UNAVAILABLE_PROFILE` in `src/lib/db.ts`). None of these are reachable through the type system - a DB column default is a string in DDL text, and the fallback constants were plain object literals, not derived from the shared `DEFAULT_AVATAR_SCHEME` constant - so TypeScript had nothing to flag. Every profile that ever fell back to a default silently carried a scheme id that matched nothing in `AVATAR_SCHEMES`, relying entirely on `getAvatarScheme()`'s `?? AVATAR_SCHEMES[0]` fallback to paper over it.

**Why it's easy to miss:** a rename inside one module (`avatarSchemes.ts`) feels complete once every *reference* to the renamed values compiles - but a default value baked into DDL text, or a duplicated literal in an unrelated file, isn't a reference the compiler tracks. `grep` for the old literal string is the only reliable way to find these, and it's easy to skip because the rename "looks done" from inside the module that owns the type.

**The fix:** pointed `DEFAULT_PROFILE`/`UNAVAILABLE_PROFILE` at the real `DEFAULT_AVATAR_SCHEME` export instead of a hardcoded literal, updated the DDL default for new installs, and added a one-time backfill (`UPDATE profile SET avatar_scheme = 'marker-yellow' WHERE avatar_scheme = 'coral'`) for rows that already had the stale value - a schema/type fix alone doesn't repair data already written under the old assumption. Also changed `getAvatarScheme()`'s own fallback from the arbitrary `AVATAR_SCHEMES[0]` to `AVATAR_SCHEMES.find(s => s.id === DEFAULT_AVATAR_SCHEME)`, so the two "what's the default" answers in the file can't drift apart from each other again.

**The reusable lesson:** after renaming a value in an enum/union type, `grep` the whole codebase (and, if applicable, existing database defaults/data) for the *old string literal*, not just for references to the type or the exported list - defaults, seed data, and DDL text hold literals the compiler will never connect back to the type they're meant to satisfy.
